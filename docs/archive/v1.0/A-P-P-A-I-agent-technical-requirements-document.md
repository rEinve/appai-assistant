## 2. Introduction and Technical Scope

### 2.1 System Background and Business Context

Traditional e-commerce purchasing tools require continuous human intervention, requiring users to manually navigate merchant web pages, evaluate item variations across unstructured HTML storefronts, and enter sensitive financial credentials into checkout forms. The Autonomous Personal Procurement Assistant Agent (A-P-P-A-I) introduces a machine-to-machine procurement architecture that eliminates manual browsing and storefront form filling.

By shifting from brittle Document Object Model (DOM) scraping to standardized API connectivity—specifically Model Context Protocol (MCP) servers, structured JSON-LD product feeds, and PayPal Agent Ready API payment rails—the A-P-P-A-I engine translates natural-language procurement queries directly into verified API checkout operations. This document specifies the technical architecture, data contracts, and security protocols required to build, test, and deploy this autonomous system.

### 2.2 Explicit Technical Goals

The A-P-P-A-I MVP engineering implementation is designed to achieve the following core technical objectives:

*   **API-First Catalog Discovery**: Implement real-time catalog parsing and inventory evaluation by connecting directly to merchant Model Context Protocol (MCP) servers and structured JSON-LD feeds.
*   **Form-Free Native Tokenized Checkout**: Execute financial transactions via direct API payloads to PayPal Agent Ready payment endpoints using single-use or merchant-scoped security tokens, completely avoiding browser form automation.
*   **Sub-Second Governance Enforcement**: Intercept every transaction attempt with a deterministic policy engine that evaluates hard spending limits (maximum item price caps and cumulative daily order caps) prior to requesting payment tokens.
*   **Automated Exception Routing**: Pause order execution and route explicit approval payloads to the user whenever an order exceeds spending thresholds or encounters policy anomalies.

### 2.3 System Non-Goals and Explicit Out-of-Scope Boundaries

To maintain technical focus and prevent scope creep during MVP implementation, the following capabilities are explicitly classified as out-of-scope for this engineering release:

| Technical Subsystem | In-Scope MVP Implementation | Explicit Out-of-Scope Boundary |
| ------ | ------ | ------ |
| **Catalog Extraction** | Structured JSON-LD feeds and standardized Model Context Protocol (MCP) catalog endpoints. | Proprietary browser DOM scraping, headless browser automation, and unstructured web parsing. |
| **Payment Execution** | Direct API checkout via PayPal Agent Ready endpoints using scoped tokens. | Direct credit card PAN processing, store-front web form filling, and multi-party split payments. |
| **Shopping Cart Scope** | Single-merchant, single-item or single-catalog order matching and execution. | Multi-merchant cart aggregation, cross-store checkout synchronization, and complex supply chain routing. |
| **Governance Architecture** | Individual user budget caps (item dollar limit, daily spend cap) and direct Human-in-the-Loop escalation. | Multi-tier corporate approval hierarchies, departmental expense routing, and dynamic corporate credit lines. |

## 3. System Architecture and Data Flow

### 3.1 High-Level Architectural Design

The A-P-P-A-I microservices architecture is structured into three primary technical pillars that operate asynchronously through event-driven API orchestration.

1.  **Catalog Discovery Engine**: Ingests user natural-language queries, converts them into structured search vectors via a Natural Language Processing (NLP) Intent Parser, and queries merchant MCP servers and JSON-LD feeds to retrieve real-time item specs, delivery timeframes, and pricing.
2.  **Governance and Guardrails Engine**: Intercepts matched items before financial token generation to evaluate hard budget controls (price caps, daily cumulative spend) and determines whether execution can proceed or requires Human-in-the-Loop (HITL) confirmation.
3.  **Tokenized Payment Execution Rail**: Communicates with the PayPal Agent Ready API to obtain single-use or merchant-scoped payment tokens and posts native order payloads directly to merchant API endpoints.

### 3.2 Sequential System Data Flow Schema

The data flow pipeline below illustrates the end-to-end execution sequence from initial user prompt input to final order confirmation and logging.

1.  **User Input Submission**: User submits natural-language prompt containing desired item attributes, delivery deadline, and price limits (e.g., "Order a replacement wireless mouse under \$50 delivered by Friday").
2.  **Intent Parsing and Extraction**: NLP Intent Parser converts prompt into structured JSON parameters: `{ item_category: "wireless mouse", max_price: 50.00, delivery_deadline: "2026-10-30", attributes: ["replacement"] }`.
3.  **Catalog Discovery Ingestion**: Discovery Engine queries connected merchant MCP endpoints and JSON-LD feeds to aggregate real-time product stock, attributes, and pricing.
4.  **Product Candidate Selection**: Engine selects optimal product match satisfying all user criteria.
5.  **Governance Pre-Check Interception**: Governance Engine intercepts product match and evaluates parameters against pre-configured database rules:
    *   *Condition A (Within Budget)*: Item Price <= `max_item_cap` AND Daily Cumulative Spend + Item Price <= `daily_spend_cap`. System proceeds to Token Request.
    *   *Condition B (Threshold Breach / Policy Exception)*: Item Price > `max_item_cap` OR Daily Spend > `daily_spend_cap`. System triggers HITL Escalation Event, pausing execution and sending notification payload to User.
6.  **Payment Token Request**: Upon Governance approval (or HITL User Confirmation), Payment Execution Module calls PayPal Agent Ready API to generate a single-use scoped payment token.
7.  **Native API Checkout Submission**: Payment Module constructs native merchant checkout API payload containing scoped payment token, shipping details, and product ID, submitting directly to merchant checkout API endpoint.
8.  **Order Logging and Telemetry**: Merchant API responds with order confirmation ID. System logs transaction metrics, updates daily spend registers, and returns success confirmation to User.

```json
}
```

### 4.4 Business Logic Rules and System State Machines

#### Budget Enforcement Logic
1.  Prior to invoking the PayPal token request endpoint, the Governance Engine retrieves `users_governance` rules.
2.  If `proposed_item_price` > `max_item_price_cap`, halt token generation and trigger HITL workflow.
3.  If `current_daily_spend` + `proposed_item_price` > `daily_spend_cap`, halt token generation and trigger HITL workflow.
4.  If both conditions pass, flag order status as `APPROVED_FOR_TOKENIZATION` and lock the daily cumulative spend delta for 15 minutes.

#### Human-in-the-Loop (HITL) Approval Workflow State Machine
*   `GOVERNANCE_HOLD` -> Notification payload sent to User mobile/web client.
*   `USER_CONFIRMED` -> Transition to `APPROVED_FOR_TOKENIZATION` -> Execute token generation and API checkout.
*   `USER_REJECTED` -> Transition to `CANCELLED_BY_USER` -> Release spend lock -> Log termination audit.
*   `TIMEOUT` (15 minutes without user response) -> Transition to `EXPIRED_HOLD` -> Release spend lock -> Terminate intent.

## 5. Non-Functional Requirements (NFRs)

The performance, reliability, scalability, and security standards for the A-P-P-A-I engine are governed by the measurable benchmarks detailed below.

### 5.1 Measurable Performance Targets

| Metric Identifier | Technical Dimension | Target Benchmark | Verification Method |
| ------ | ------ | ------ | ------ |
| **NFR-PERF-01** | **Catalog Query Latency** | <= 500 ms (p95) across MCP / JSON-LD queries | Synthetic API latency monitoring |
| **NFR-PERF-02** | **Governance Evaluation** | <= 100 ms execution time for spend cap checks | Benchmark unit testing on policy engine |
| **NFR-PERF-03** | **End-to-End Execution** | <= 3.0 seconds total prompt-to-checkout API submission | End-to-end integration test automation |
| **NFR-PERF-04** | **Token Generation Latency**| <= 400 ms response time from PayPal Agent Ready endpoint | External API latency tracing |

### 5.2 System Availability and Reliability

*   **NFR-REL-01 (Orchestration Uptime)**: Core microservices orchestration services must maintain 99.9% availability during operational hours.
*   **NFR-REL-02 (Transaction Atomicity)**: Checkout API operations must be fully transactional. If native merchant API submission fails after token generation, the token must be immediately invalidated via PayPal API revocation endpoints.

### 5.3 Scalability and Data Retention

*   **NFR-SCA-01 (Horizontal Auto-Scaling)**: Discovery ingestion microservices must auto-scale horizontally to support concurrent catalog query spikes up to 100 requests per second (RPS).
*   **NFR-RET-01 (Zero Raw Financial Storage)**: System databases shall store zero primary account numbers (PAN), CVVs, or raw PayPal account passwords. Only anonymized token reference hashes (`payment_token_ref`) and order confirmation IDs may be persisted.
*   **NFR-RET-02 (Audit Trail Retention)**: Transaction and governance logs (`transaction_logs`, `order_intents`) must be retained in encrypted read-only storage for a minimum of 7 years to satisfy financial audit compliance.

## 6. Security and Compliance Protocols

### 6.1 Authentication and Transport Layer Standards

All communication between A-P-P-A-I microservices, merchant MCP endpoints, and the PayPal Agent Ready API must enforce strict encryption and identity verification:

*   **Transport Layer Security**: All external HTTP communication strictly requires TLS 1.3 encryption. Unencrypted HTTP traffic is rejected at the API gateway level.
*   **Service Authentication**: Microservice-to-microservice communication requires mutual TLS (mTLS) with cryptographically signed JSON Web Tokens (JWT) for payload authorization.
*   **MCP Endpoint Security**: Interactions with merchant Model Context Protocol servers must authenticate via OAuth 2.0 bearer tokens or signed API keys.

### 6.2 Scoped Payment Token Security Model

To satisfy the zero credential exposure requirement (MTR-03 and NFR-01), the payment subsystem implements a strict token isolation model:

1.  **No Credential Ingestion**: The AI agent, NLP parser, and discovery database have zero interface paths for receiving, storing, or transmitting credit card numbers or raw bank credentials.
2.  **Single-Use Authorization**: PayPal Agent Ready payment tokens are bound strictly to a single `merchant_id` and a maximum authorized dollar amount.
3.  **Ephemeral Lifespan**: Issued tokens automatically expire after 15 minutes if not submitted to the target merchant checkout endpoint.

### 6.3 Role-Based Access Control (RBAC) and Privacy

The system enforces strict permission boundaries between automated agent execution and user administrative actions:

*   **Agent Role (`role_agent`)**: Permitted to read catalog feeds, execute budget pre-checks, request scoped tokens, and submit native checkout API payloads within approved limits. Prohibited from modifying user budget caps or bypassing HITL holds.
*   **User Role (`role_user`)**: Permitted to configure hard budget caps, view transaction audit logs, and approve/reject HITL escalation holds.
*   **Data Privacy**: All personally identifiable information (PII)—including user shipping addresses and full names—must be stored encrypted at rest using AES-256 encryption.

### 7.3 Edge-Case and Failure Recovery Matrix

| Failure Scenario | Technical Root Cause | System Recovery Behavior | Impact Mitigation |
| ------ | ------ | ------ | ------ |
| **Stale JSON-LD Feed** | Merchant catalog pricing updated after ingestion but prior to checkout. | Pre-checkout real-time re-verification (NFR-03) detects price discrepancy. Governance re-evaluates new price before token request. | Prevents unauthorized price overrun. |
| **Token Acquisition Timeout** | PayPal Agent Ready API endpoint latency exceeds 400 ms. | Payment module cancels transaction request, returns HTTP 504 Gateway Timeout, and logs token timeout event. | Prevents hanging agent states. |
| **User HITL Timeout** | User fails to respond to approval request within 15 minutes. | Governance state machine transitions hold from `GOVERNANCE_HOLD` to `EXPIRED_HOLD`. Pending spend lock is released. | Frees locked daily spend quota. |
| **Merchant API Error** | Merchant checkout endpoint returns HTTP 500 Internal Server Error. | System triggers immediate PayPal token revocation API call and flags transaction as `FAILED_MERCHANT_EXECUTION`. | Ensures zero financial loss on failed orders. |

## 8. Deployment and Rollback Plans

### 8.1 Release Steps and Delivery Sequence

Engineering execution is organized across three sequential microservice deployment milestones aligned with the project sprint roadmap:

1.  **Sprint 1 Milestone (Discovery Engine Baseline)**: Deploy containerized Discovery microservice, database schemas (`order_intents`), MCP server adapters, JSON-LD ingestion parsers, and NLP intent extraction pipelines.
2.  **Sprint 2 Milestone (Tokenized Payment Rail Integration)**: Deploy Payment Execution microservice, integrate PayPal Agent Ready developer endpoints, implement single-use token handlers, and build native merchant checkout API payload builders.
3.  **Sprint 3 Milestone (Governance & Final System Sign-off)**: Deploy Governance microservice, implement deterministic hard spend cap checkers, build HITL push notification/approval workflows, and conduct end-to-end security penetration testing.

### 8.2 Database Migration Strategy

Database updates for entity schemas (`users_governance`, `order_intents`, `transaction_logs`) are managed using transactional schema migration scripts:

*   Migration scripts must execute within idempotent transactions.
*   Rollback migration scripts (`V1.0__rollback.sql`) must be pre-tested in staging environments prior to production release.

### 8.3 Telemetry, Monitoring, and Alerting

Production monitoring tracks operational health across all three pillars using real-time metric dashboards:

*   **Alert Rule ALT-01 (High Governance Intercepts)**: Trigger warning alert if HITL escalation rate exceeds 25% of total orders over a rolling 1-hour window (indicates misconfigured default budget caps).
*   **Alert Rule ALT-02 (Token Generation Failure)**: Trigger critical alert if PayPal Agent Ready token generation failure rate exceeds 2% over a 5-minute window.
*   **Alert Rule ALT-03 (Latency Spike)**: Trigger alert if p95 catalog ingestion latency exceeds 800 ms.

### 8.4 Circuit Breakers and Rollback Protocols

In the event of critical system instability or unexpected execution failures, automated circuit breakers protect user assets:

*   **Global Execution Circuit Breaker**: If three consecutive transactions experience unhandled payment execution errors, the system automatically transitions all active agent execution pipelines to `SAFE_MODE_PAUSE`, routing 100% of subsequent procurement requests to mandatory HITL confirmation.
*   **Service Rollback**: Individual microservices (Discovery, Payment, Governance) are deployed as independent container groups. Rolling back a service to its previous stable image tag requires zero downtime for adjacent operational modules.
