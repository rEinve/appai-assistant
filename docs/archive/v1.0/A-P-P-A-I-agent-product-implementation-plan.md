## 2. What We Are Building First (Immediate MVP Scope)

To deliver commercial utility rapidly while minimizing architectural exposure, the engineering deployment prioritizes the core autonomous purchasing engine across three non-negotiable technical pillars.

```
+-----------------------------------------------------------------------------------+
|                            A-P-P-A-I MVP CORE ENGINE                              |
+--------------------------+--------------------------+-----------------------------+
|    Catalog Discovery     |    Governance Engine     |  Tokenized Checkout Rail    |
|   (MCP & JSON-LD Feeds)  |  (Hard Caps & HITL Flow) | (PayPal Agent Ready Tokens) |
+--------------------------+--------------------------+-----------------------------+
```

### 2.1 Scope Prioritization Rationale

1.  **Pillar 1: Catalog Discovery Engine (FR-01, FR-02, FR-03)**
    *   *Core Capability*: Ingestion of structured inventory via Model Context Protocol (MCP) servers and JSON-LD feeds, paired with natural-language intent parsing to extract required item attributes, delivery deadlines, and price ceilings.
    *   *Rationale*: Autonomous shopping cannot occur without real-time, deterministic product matching. Bypassing brittle web scraping in favor of standard feeds ensures high matching accuracy.
2.  **Pillar 3: Governance and Guardrails Engine (FR-06, FR-07)**
    *   *Core Capability*: Deterministic pre-checkout evaluation enforcing hard budget limits (`max_item_price_cap` and `daily_spend_cap`) and routing threshold exceptions to Human-in-the-Loop (HITL) approval workflows.
    *   *Rationale*: Financial safety must be established before executing automated API payments. Sub-second governance checks prevent runaway spend overruns.
3.  **Pillar 2: Tokenized Payment Execution Rail (FR-04, FR-05)**
    *   *Core Capability*: Direct API checkout via PayPal Agent Ready payment rails utilizing single-use or merchant-scoped payment tokens.
    *   *Rationale*: Replaces raw card credentials with scoped tokens, eliminating financial credential exposure and avoiding browser form filling.

### 2.2 Explicit Deferrals (Post-MVP Scope)

To prevent scope creep, the following capabilities are explicitly barred from initial sprint execution:
*   Multi-merchant split cart aggregation.
*   Unstructured HTML DOM web scraping fallbacks.
*   Multi-tier corporate expense approval hierarchies.

## 3. Planning Assumptions to Review

The success of this implementation plan relies on several core architectural and operational assumptions established in the product discovery baseline.

### 3.1 Technical and Integration Assumptions

1.  **Standardized Catalog Feeds**: Target merchant endpoints expose valid JSON-LD structured data or operate compliant Model Context Protocol (MCP) catalog servers containing real-time price and stock attributes.
2.  **Payment Rail API Availability**: Sandbox and production developer access to PayPal Agent Ready API endpoints is active, enabling real-time generation of single-use and merchant-scoped payment tokens.
3.  **Zero Raw Credential Architecture**: The AI model and application microservices will never ingest, store, or process raw credit card primary account numbers (PANs) or CVVs.
4.  **Sub-Second Governance Latency**: Budget enforcement rules and Redis-backed daily spend state updates execute with sub-second latencies prior to token generation calls.

## 4. Phase Breakdown & Implementation Contracts

The implementation is structured into four sequential phases, starting with Milestone 0 (M0) to establish the delivery contract and governance baseline.

*   **State Output**:
    *   Fully provisioned local and staging development environments.
    *   Committed PostgreSQL schema migrations (`users_governance`, `order_intents`, `transaction_logs`).
    *   Validated OpenAPI 3.0 specification contracts for all microservices.
*   **Breakdown into Manageable Tasks**:
    *   *Task M0-1*: Configure multi-module repository structure (`/discovery`, `/governance`, `/payment`, `/common`).
    *   *Task M0-2*: Write and execute SQL schema migration scripts for user profiles and audit registers.
    *   *Task M0-3*: Implement centralized Redis cache cluster for daily spend tracking.
    *   *Task M0-4*: Setup GitHub Actions CI/CD pipeline enforcing static code analysis and unit test thresholds (>85%).
*   **Exit Gate**:
    *   All microservice skeleton containers pass health-check tests in local Docker environments.
    *   Database migrations run cleanly with zero errors; test data seeded successfully.
    *   OpenAPI contract mock servers responding with 200 OK across all endpoints.
*   **Review Protocol**:
    *   Architecture review meeting with Lead Systems Architect and Security Lead to verify zero credential exposure in contract schemas.

### 4.2 Phase 1: Catalog Discovery Engine (Milestone M1)

Phase 1 delivers the natural-language query parser and structured catalog connectors.

*   **State Output**:
    *   Operational Discovery Microservice handling intent parsing and catalog ingestion.
    *   Natural-Language Processing (NLP) Intent Parser converting user text into structured JSON constraints.
    *   Model Context Protocol (MCP) client and JSON-LD parser modules.
*   **Breakdown into Manageable Tasks**:
    *   *Task M1-1*: Implement Intent Parser using LLM structured output schemas to extract `item_keyword`, `max_price_constraint`, and `delivery_deadline`.
    *   *Task M1-2*: Build JSON-LD Feed Fetcher with schema validation to parse `http://schema.org/Product` data.
    *   *Task M1-3*: Implement MCP Catalog Client to query connected merchant catalog endpoints via RPC/JSON-RPC.
    *   *Task M1-4*: Develop Product Matching Engine to score candidate items against user constraints and select the optimal match.
*   **Exit Gate**:
    *   Intent Parser achieves >95% accuracy on standard benchmark procurement prompt dataset.
    *   Catalog Engine successfully fetches, validates, and filters products from mock MCP and JSON-LD endpoints within <1.5 seconds.
    *   Integration test suite passes for end-to-end prompt-to-product selection flow.
*   **Review Protocol**:
    *   Sprint review demonstration showing live natural-language prompts parsed into matched product candidate payloads.

Phase 2 integrates the PayPal Agent Ready payment rail for secure tokenization and native API checkout.

    *   *Task M2-3*: Construct Merchant API Checkout Client to submit native purchase payloads containing payment tokens and delivery addresses.
    *   *Task M2-4*: Implement transaction result parser and audit log recorder for `transaction_logs` table.
*   **Exit Gate**:
    *   100% successful execution of test purchases in PayPal sandbox without web form navigation.
    *   Verification that raw card credentials are completely absent from network traffic and log dumps.
    *   Automated rollback mechanism verified for failed merchant API checkout calls.
*   **Review Protocol**:
    *   Security sign-off auditing tokenization logs and network packet captures for zero raw credential leakage.

### 4.4 Phase 3: Governance, Guardrails & Human-in-the-Loop (Milestone M3)

Phase 3 builds the pre-checkout budget enforcement module and Human-in-the-Loop approval workflows.

*   **State Output**:
    *   Production-ready Governance Microservice operating sub-second budget checks.
    *   Redis atomic spend counter updater.
    *   Human-in-the-Loop (HITL) exception notification dispatcher and approval webhook handler.
*   **Breakdown into Manageable Tasks**:
    *   *Task M3-1*: Implement Rule Engine evaluating `max_item_price_cap` and `daily_spend_cap` against requested order amounts.
    *   *Task M3-2*: Implement atomic Redis operations for real-time daily spend accumulation and budget checks.
    *   *Task M3-3*: Build HITL Escalation Handler to pause order processing and issue user approval payloads upon rule breach.
    *   *Task M3-4*: Build Webhook Gateway to receive user approval/rejection signals and resume or terminate execution.
*   **Exit Gate**:
    *   100% of out-of-budget test orders blocked prior to payment token generation calls.
    *   100% of policy exception orders correctly routed to HITL notification queues.
    *   Sub-second (<200ms) execution time for governance evaluation rules under simulated peak load.
*   **Review Protocol**:
    *   Final production sign-off meeting reviewing end-to-end System Acceptance Test (SAT) results across all four success metrics (MTR-01 through MTR-04).

## 5. Proposed Code Boundaries & System Architecture

The codebase is organized into modular, decoupled microservices with strict isolation parameters to enforce security and clean domain separation.

```
/appa-agent-core/
├── /cmd/
│   ├── /discovery-service/       # Catalog Discovery Entrypoint
│   ├── /governance-service/      # Governance & Rule Engine Entrypoint
│   └── /payment-service/         # Tokenized Payment Rail Entrypoint
├── /pkg/
│   ├── /mcp/                     # Model Context Protocol Client Library
│   ├── /jsonld/                  # JSON-LD Product Feed Parser
│   ├── /paypal/                  # PayPal Agent Ready API Client
│   └── /rules/                   # Governance Rule Engine Logic
├── /internal/
│   ├── /domain/                  # Shared Entities (Users, Intents, Transactions)
│   ├── /repository/              # Database Access Layer (PostgreSQL & Redis)
│   └── /middleware/              # Auth, Logging, Telemetry
└── /migrations/                  # SQL Database Migration Scripts
```

### 5.1 Service Isolation Parameters

*   **Payment Service Boundary**: Strictly isolated from the NLP Intent Parser and external web clients. Communicates only with the Governance Service via encrypted internal gRPC/mTLS channels.
*   **Governance Service Boundary**: Has read/write access to `users_governance` PostgreSQL tables and Redis spend caches. Acts as an mandatory gatekeeper before calling the Payment Service.
*   **Discovery Service Boundary**: Performs outbound read-only HTTPS calls to merchant MCP servers and JSON-LD feeds. Possesses zero access to payment APIs or user financial records.

## 7. Risks and Decisions That Can Change the Plan

A proactive risk management matrix identifies technical threats that could impact delivery timelines or require architectural pivots.

| Risk ID | Identified Risk / Threat | Severity | Impact | Mitigation / Contigency Plan |
| ------ | ------ | ------ | ------ | ------ |
| **RSK-01** | **Merchant Feed Non-Compliance**<br>Merchant feeds lack required JSON-LD attributes or MCP endpoints. | Medium | Discovery Engine fails to retrieve stock or pricing data accurately. | Enforce strict feed schema validation; reject non-compliant merchant feeds and alert user. |
| **RSK-02** | **Payment API Latency**<br>PayPal Agent Ready token generation exceeds SLA timeouts. | High | Checkout flow stalls or fails to complete within threshold windows. | Implement circuit breakers and exponential backoff retry logic on token requests. |
| **RSK-03** | **Budget Check Race Conditions**<br>Simultaneous order attempts bypass daily spend limits. | High | Cumulative user spending exceeds configured daily cap. | Enforce atomic Redis transactional increments (`INCRBYFLOAT`) during governance pre-checks. |
